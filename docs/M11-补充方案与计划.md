# M11 补充方案与计划：MCP + agent 编排 + 双联网源 + 记忆证据 + wiki 沉淀

> 承接调研结论：差异化靠"评测证据 + 决策链 + 失败/成本叙事 + 工具化"，不靠加功能。本方案把已有卖点焊实，再叠加区分度高的增量。

## 0. 定位（一句话）
Bagent = 面向团队的"会积累的可信研究助手"：私有库⊕联网多源取证、冲突/可信度把关、产出带引用文档、把结果沉淀回知识库。**多租户工程项挪到独立 Java 项目**，本项目专注 AI 应用深度。

## 1. 优先级（ROI 排序，先焊已有、再加新的）
| 优先级 | 事项 | 为什么 | 现状/工作量 |
|---|---|---|---|
| P0 | **写回记忆端到端证据**（含错网络结论→门控开/关→污染率） | 我们最大卖点"越用越准不越用越脏"目前**只有机制无端到端数据**，会被追穿 | 复用 counterfactual+CI harness，小 |
| P0 | **"评测即故事"显性化**（README 顶部放消融/CI 数字 + workflow-vs-agent 边界一节） | 调研里拉差距的第一项，近乎零成本 | 文档整理 |
| P1 | **显式 agent 编排 + 轨迹评测**（有界 plan-execute/ReAct、trajectory eval、HITL 确认点） | 京东/快手必问，"及格线之上" | 中，复用 self-RAG/research |

## 2. MiMo 联网：架构判断（关键，别塞错层）
**事实**（官方定价页）：联网服务插件 **国内 ¥16/1000 次**，**含网页搜索 + 网页解析**，按次独立计费。它是**模型自带的"搜+读+综合"**，不是返回一堆链接让我们自己处理的 SERP API。

**因此它和 SearXNG 是两类东西，不能塞进同一个槽：**
| | SearXNG（现有） | MiMo 联网 |
|---|---|---|
| 形态 | **检索即工具**：我们拿候选/证据，喂任意 LLM | **模型自带搜索**：一次调用直接出 web 接地的**答案** |
| 掌控度 | 高（候选、去重、引用、冲突、trust 都在我们手里） | 低（黑盒，搜索与 MiMo 生成融合） |
| 成本 | 自架 + 上游限流 | ¥0.016/次 + token |
| 依赖 | 无 key | 需以 MiMo 为调用模型 |

**结论/我的设计**：把 MiMo 联网**做成"第二意见/佐证源"(WebGroundedAnswerSource)，而不是硬套 SearchProvider**。价值点：
- **多源佐证治反事实**：同一个问题，KB-RAG 答案 vs MiMo-联网答案**并行**产出 → 过我们已有的 `detect_conflict` → 显式标"内部资料说 X、实时联网说 Y"。这比把它当搜索源更能发挥它的独立价值（不同 provider = 天然独立性）。
- **联网降级备份**：SearXNG/百度挂了时，仍有 web-grounded 路径。
- 可选再做一个薄 `MiMoWebSearchProvider`（prompt 强约束返回 JSON 结果列表）塞进 `SearchProvider`——但那是"花模型调用买 SERP"，性价比不如 SearXNG，只作备选，**不作主用**。
> 一句话：我倾向 **MiMo 联网 = 佐证/第二答案源（generator/orchestrator 层）**，而不是第 3 个检索 provider。这与用户最初"作为另一种联网能力"的直觉一致，只是归到正确的层。

## 3. MCP server（对外封装）
用 Python MCP SDK 起一个 server，工具直接调现有服务函数（复用逻辑，不重写）：`kb_search(query,top_k)`、`kb_answer(query)`、`web_search(query)`、`research(topic)`、`memory_add/search/list`。收益：① 简历"工具化/可组合"硬信号；② 能被 Claude/Cursor 当后端知识库用（demo 直观）；③ 与 REST 并存，展示接口分层。鉴权：本地/带 API-Key，工具参数走结构化 schema。

## 4. agent 编排 + 轨迹评测
把 rewrite→retrieve→self-RAG→(web∥MiMo)→synthesize 收进**一个显式有界循环**：工具注册表(kb/web/mimo-web/calc)、plan-execute、**max_steps/成本/token 预算**、失败恢复、HITL 关键点(如写回/高成本动作前确认)。**轨迹评测**：记录每步 action/observation/理由，跑固定任务集，测"步数分布、无效循环率、收敛率、最终质量"。明确划 workflow(可枚举流程)与 agent(动态取证)边界，别为酷上多 agent。

## 5. wiki/沉淀
research 文档 → 生成结构化"知识页"(topic/结论/引用/来源/时效)，落 draft；人工/多源佐证 promote 进正式库，形成可浏览的 wiki。复用 memories 表 + trust 生命周期，不新造体系。

## 6. 建议执行顺序
**先做 §1 的两个 P0（焊证据、写故事）→ 再做 MiMo 佐证源(P2 提前，因为小且直接补强多源)→ MCP server → agent 显式循环+轨迹评测 → wiki 沉淀。** 每步都带测试/CI/文档，完成即完成。
